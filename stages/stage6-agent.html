Stage 6

ReAct agents & harness engineering

Everything so far converges here: a model that reasons out loud, acts on real files without me approving each step, decides on its own when it's done — and is then checked by a second model that doesn't trust it.

What I built

An autonomous coding agent in Python. Given one instruction ("add input validation to read_note, here's what failure should look like"), it reads the real file, makes a precise edit, and stops when it judges the goal met — no human in the loop between steps. Then a separate model call, shown only the goal and the final file, grades it PASS or FAIL.

Key concepts

What's an "agent"?

Worth pinning down, since I've used the word loosely. On its own a model does one thing: read text, predict the next text, stop — a single inference pass, with no memory or actions. An agent wraps that one-shot model in a loop with tools and memory so it can pursue a goal across many steps on its own: the model is the brain, and the agent is everything around it that lets it act, remember, keep going, and check its own work (the formal name for that wrapper is the harness). You've already built every piece — this stage just names the whole.

ReAct is just one line in the prompt

I expected ReAct ("Reason + Act" — from a 2022 paper, Yao et al.) to be a library or a special API. It isn't. It's a single instruction asking the model to write a brief Thought: before each tool call. Mechanically it's the exact same agent loop from Stage 3 — the only change is that the model's reasoning becomes visible text instead of an opaque decision. That visibility is the point: when the agent misbehaves, you can see why. (You'll see the actual one-line instruction in the code below.)

"Reason" in ReAct isn't the model's reasoning

ReAct stands for "Reason + Act," which tripped me up — because "reasoning" is also the word for a model's trained extended thinking. They are not the same thing:

ReAct's "Reason" — the Thought: lineThe model's reasoning — extended thinking
What it is A prompted habit: you ask the model to type a one-sentence Thought: before each tool call. A trained capability: private step-by-step thinking the model does before answering, baked in during training.
Where it lives In your system prompt — works on any model. In the model's weights — a toggle on capable models.
Visible? Yes — it's plain output text; that's the whole point. Usually hidden, or shown only summarized.

They can even combine — a reasoning model running a ReAct prompt does both. And one more word ties the room together: inference is just the umbrella act of running the model to produce any output at all. Reasoning and tool-calling are things that happen during an inference, not separate "modes" you switch between.

And worth stressing about that tool-calling: emitting a structured function_call is itself a trained capability, just like reasoning. Early dialogue-only models couldn't reliably produce the exact format — they'd write a plausible sentence about calling a tool instead. Both abilities are baked into the model by training, not summoned by a clever prompt alone.

A rapidly evolving vocabulary

Most of this stage's terminology is new — some of it named only months ago — and it mostly sorts onto one ladder, where each rung answers "how much of the work does the human still trigger, turn by turn?"

The split that matters: the top two rungs only shape a single response — that's not an agent yet. The agent concept begins at the harness rung, where a model runs in a loop with tools and memory, pursuing a goal across many steps. This stage's agent is that third rung.

How new is all this? Harness engineering was named publicly around February 2026 (Mitchell Hashimoto's "engineering the harness," quickly picked up by OpenAI and Anthropic); loop engineering only in June 2026 (Addy Osmani, building on Peter Steinberger and Anthropic's Boris Cherny) — the latter explicitly "still early" and contested. The ideas moved faster than the words for them.

Further reading: "Harness engineering for coding agent users" (Böckeler, martinfowler.com) and "Loop Engineering" (Addy Osmani).

Harness engineering: "Agent = Model + Harness"

The harness is everything around the model that makes it a working agent: tools to act, memory to remember, a loop to keep going, verification to check the work, guardrails to stay safe. How much does it matter? On the same benchmark, the same model scores very differently depending only on its harness — one analysis found three agents running an identical model landing ~5 points apart, and puts the typical swing from harness choices alone at 10–20 points (SWE-bench scaffolding analysis).

It's not proof, but I saw the same separation first-hand. Mid-build I swapped the model from Gemini Flash-Lite to Gemma (same hosted Google API, for better token throughput). Because Gemma also has trained function-calling, my loop, tools, and parsing all ran unchanged — I edited one model-name string. The harness had made the two models more or less interchangeable behind it; that's the whole idea of treating them as separate layers.

Gotchas & lessons

An agent hammers the rate limit

A chat is one request per turn. An agent loop can call the model many times for a single goal, and the context grows every round — so it's far more demanding than a chatbot and hits rate limits much faster. The harness has to plan for that: pace the calls, retry on a 429, and cap every tool result so the context can't balloon. (The exact limit numbers shift without notice — always check your own provider dashboard, never an article.)

Don't trust an agent's own "done"

A model grading its own work overpraises it — so "done" reported by an agent is a claim, not a proof. The fix is the generator/verifier split: a separate, deliberately skeptical model checks the result, shown only the goal and the final file, with no idea how the agent reasoned. In my run it independently agreed the edit was correct — which is the only reason that "done" meant anything.

The core mechanic, in code

First, the entire "ReAct" mechanism — it really is one instruction in the system prompt:

demos/06-agent-python/agent.py 
AGENT_SYSTEM_PROMPT = """You are an autonomous coding agent.
... mission and rules ...

Before every tool call, briefly state your reasoning in one
sentence, prefixed with "Thought:". This is for the human
reading the trace, not for the user.
..."""

That single Thought: line is all ReAct is. The rest is harness plumbing — here, a guard that refuses to repeat a dead action, and the verifier as a deliberately separate call:

demos/06-agent-python/agent.py 
# inside the loop — refuse to burn quota repeating a dead action
call_signature = (fc.name, json.dumps(args, sort_keys=True))
if call_signature in seen_calls:
    result = ("You already called this exact tool with these exact "
              "arguments. Try something different or finish.")
else:
    seen_calls.add(call_signature)
    result = _truncate(execute_tool(fc.name, args))   # cap the result size

# the verifier — a SEPARATE call, given only the goal + final file
def verify(goal, path):
    content = _truncate(read_file(path), limit=4000)
    return generate(
        contents=f"GOAL: {goal}\n\nFILE ({path}):\n{content}",
        system_instruction=VERIFIER_SYSTEM_PROMPT,
    )  # it never sees the agent's reasoning — that's the point
  1. The system prompt is where ReAct lives — one line asking for a Thought: before each tool call. No library, no special API.
  2. The call signature is the tool name plus its exact arguments. If the agent asks for the identical call again, that's usually a stuck loop.
  3. The guard doesn't run the repeat — it replies with a nudge to change approach or finish, so a missing-file loop can't quietly drain the quota.
  4. verify is a fresh call with a skeptical system prompt, given only the goal and the finished file. Because it never sees how the agent reasoned, a PASS means something.

A different axis: Spec-Driven Development

One term I picked up doesn't belong on the ladder above at all. The prompt→context→harness→loop progression all answers "how autonomous is the agent." Spec-Driven Development answers a different question — "how rigorously is intent specified before any agent acts?" — by writing a structured, testable spec up front. Sources genuinely disagree on whether it nests inside context engineering or pairs with harness engineering, and there's no settled taxonomy yet. I'm noting it as a lens rather than a rung; I haven't built a demo around it, so it may earn its own page someday.
