Stage 5

MCP — connect any tool to any AI app

Stage 3's tools lived inside one script. MCP is the standard that lets any AI app reach any tool or data server — so a thing you build once can plug into Claude Desktop, the CLI, or your own host.

What I built

A small MCP server that exposes my notes folder as three tools — list_notes, read_note, search_notes — that any MCP-speaking app can connect to and call. The same server can run two ways (a local process or a networked server), which is the point: a server's logic and its transport are separate concerns. The how-to-run details (and a gnarly Docker bug from building it) are in the README.

View the demo & README on GitHub

A bit of history

MCP isn't a Google or Python thing — Anthropic introduced it in late 2024 and open-sourced the spec. Because it's open, other AI apps and tool vendors adopted it rather than each inventing their own plug-in format, and it's quickly become a de-facto common standard. That's the whole appeal: a server you write to the standard works in any host that speaks it.

Key concepts

Three roles in one sentence

MCP (the Model Context Protocol) splits the world into three roles:

RoleWhat it isWho normally provides it
HostThe app the human uses — Claude Desktop, the CLI, an IDE.The app vendor
ClientBuilt into the host; speaks the protocol to one server.The app vendor
ServerExposes tools or data over the protocol.A tool/service provider or the community — or you, if you're wrapping your own data (as in this demo)

The protocol, concretely

Underneath it's just JSON-RPC 2.0 messages. A client calls tools/list to discover what a server offers — name, description, and a parameter schema, the exact same shape as a Stage 3 tool definition. To invoke one it calls tools/call with the name and arguments, and the server returns a result. The LLM never talks to the server directly — it only emits "call tool X with these args," and the client inside the host is what actually sends the request.

To the model, all tools look the same

This is the insight that ties the stage together. Local functions (Stage 3) and MCP tools get merged into one flat list before they reach the model — identical shape either way. The model picks a tool purely by name and description; it has no idea which is local and which lives on a remote server. All the routing back to where a tool actually lives happens after the model responds, in the host's private lookup table.

The practical consequence is the lesson below: names have to stay unique across everything you connect.

Popular MCP servers

The reason MCP caught on is that you rarely have to build a server at all — there's usually one already for whatever you want to connect. Anthropic ships a set of reference servers, and there's a large ecosystem of community and vendor ones on top. A sampler:

CategoryExample servers
Files & codeFilesystem, Git, GitHub / GitLab
DatabasesPostgreSQL, SQLite
Web & browserFetch, Brave Search, Puppeteer / Playwright
SaaS & productivitySlack, Google Drive, Notion, Linear, Stripe
MemoryMemory — a knowledge-graph store the agent writes to and reads back

Connect any of these and its tools simply join the same flat list the model already sees — a GitHub server's create_issue ends up right next to your own read_note, indistinguishable to the model. Those tools are the very same name + description + schema shape from Stage 3; that's the whole payoff of a shared standard.

Browse more: the official reference servers (Filesystem, Git, Fetch, Memory, …), the official MCP Registry, and community directories like mcpservers.org and Glama. The ecosystem has grown into the tens of thousands of servers since late 2024.

MCP, tools, and skills — what's the difference?

I kept conflating these. Untangling them:

What it isTo the model
Plain tool A function wired directly into one app's own code. Identical — both arrive as a name, description, and parameter schema it can request. The model can't tell them apart.
MCP tool A tool reached over the standard, so any host can connect it with no bespoke integration code.
Skill Lazily-loaded instructions for doing something. Guidance, not a callable tool — and carrying it out still means calling tools.

In short: an MCP tool and a plain tool are the same kind of thing — a capability the model can call, differing only in how they're wired up. A skill isn't a capability at all; it's guidance, and acting on it still comes down to calling tools. Capabilities and guidance combine — one doesn't replace the other.

Living with MCP — lifecycle & cost

  • Add / remove isn't live. Changing the connected-server list doesn't update a running session in real time. Depending on the agent, the change lands only after you relaunch the app or start a new chat session.
  • Updates can be live. An already-connected server can change its tool list mid-session by pushing a notifications/tools/list_changed, telling the client to re-fetch tools/list without a restart.
  • Context cost is real. Every connected server's tool descriptions are sent on every request — the same context bloat from Stage 3, but easier to trigger by accident, since connecting one server can silently add 20+ tools at once.

Gotchas & lessons

Tool names must be globally unique

Because the model sees every tool — local and MCP — in one flat list and picks purely by name, two tools sharing a name make both the model's choice and the host's routing ambiguous. Across everything you connect at once, names have to be unique.

The core mechanic, in code

A factory builds the server once — tools and all — and the same server is then served over whichever transport you pick.

demos/05-mcp-python/notes_core.py · run_stdio.py 
# notes_core.py — one factory builds the server, tools defined once
def create_server() -> FastMCP:
    mcp = FastMCP("notes-server")

    @mcp.tool()
    def read_note(filename: str) -> str:
        """Read the full content of a specific note file by name."""
        ...
    return mcp

# the SAME server, exposed over a chosen transport:
mcp = create_server()
mcp.run(transport="stdio")             # a local subprocess the host launches
# mcp.run(transport="streamable-http")  # a networked server apps connect to
  1. The factory builds an identical server each call — the same tools, the same logic — independent of how it'll be served.
  2. @mcp.tool() registers a normal Python function as an MCP tool. The docstring becomes the description the model reads — so it's not a comment, it's part of the interface.
  3. mcp.run(transport=...) picks how the server is exposed: "stdio" runs it as a local subprocess the host spawns; "streamable-http" runs it as a networked server apps connect to. Same server, different door in — the network details live in the README.
