Stage 1

Multi-turn chatbot & the context window

The smallest possible AI app — a chatbot in a terminal — taught me the one thing everything else is built on: the model has no memory.

What I built

A command-line chatbot in Python. You type, it replies, you type a follow-up, and it answers as if it remembered the conversation. A couple dozen lines — trivial on the surface. The value was entirely in what it forced me to understand about why that "memory" works at all.

View the demo & README on GitHub

Key concepts

My first instinct was that a chat session is a long-lived object on a server holding state. It isn't. A model is stateless: every call is independent and it remembers nothing from the last one.

So how does a follow-up like "what did I just ask?" work? Because the "memory" is a trick I repeat every turn — I resend the entire conversation so far on every single request. The demo keeps that conversation in a plain list and resends it by hand (instead of letting an SDK helper hide it), so you can actually watch the list — and the context it costs — grow with every turn.

Three terms fall out of this, and they recur for the rest of the journey:

  • Token — the unit a model reads in: a subword piece, not a whole word (~4 characters of English on average). More on this just below.
  • Context window — the total text a model can consider at once. History, system prompt and your new message all share this one budget, so it can't grow forever.
  • System prompt — a persistent instruction set, separate from the conversation, that sets the model's role ("you are a helpful assistant for a developer learning AI").

So what's a token, really?

This one tripped me up. The shorthand "1 word ≈ 1 token" describes the old way tokenizers worked, not what modern models do. Today a token is a subword piece — usually a chunk of a word, sometimes a whole short word, sometimes just a space or a punctuation mark. Here's a real split from the GPT tokenizer — this one sentence is 17 tokens, each a coloured block below:

I am an AI assistant working with a tokenizer; tokenization isn't always intuitive.

Common words are usually one token (the colour starts at the leading space). But tokenizer/tokenization show how a longer word breaks up — token + ization — isn't splits into isn + 't, and punctuation gets its own token. That's why word counts and token counts never quite line up.

How the pieces get chosen

The mainstream method is Byte-Pair Encoding (BPE) (GPT, Llama), with close relatives like WordPiece and SentencePiece (Gemini). The key word is byte: the text is first turned into its raw UTF-8 bytes, and the tokenizer repeatedly merges the most frequent adjacent pair into a new piece. Frequent words become a single token, rare ones fall back to smaller pieces, and nothing is ever truly "unknown" — worst case, a token is one raw byte.

That cuts both ways — and it's about frequency, not characters. A rare character can split into its raw bytes (謝 = three tokens in GPT-4), while a common word merges into one (好き = one token in GPT-5). English still averages ~4 characters per token; most other languages pack more.

Want to see it for real? Paste any text into a live tokenizer and watch it split: OpenAI's tokenizer or gpt-tokenizer.dev.

The questions I actually had about it:

QuestionAnswer
Is the tokenizer itself an AI model? No — not a neural network. Its vocabulary is learned from a corpus (which pairs of characters occur together most), but at runtime it's a fast, deterministic split-and-lookup. No GPU, no guessing.
Can a model use any tokenizer? No. Each model is trained with one fixed tokenizer — its token IDs are baked into the model's internal tables. Swap the tokenizer and the IDs become meaningless. Model and tokenizer are a matched pair.
Where does tokenizing run? When you call a hosted API, it runs on the provider's server, right before the model. The vocabulary is usually public, though, so you can also run the same tokenizer locally to estimate counts before sending.
If it runs on their server, how do I know my token count? Two ways: providers expose a count-tokens call, and every response comes back with a usage block — prompt tokens, output tokens, total. You read the cost back from the reply.

Gotchas & lessons

Getting access

With a Google account, Gemini API access is quick to get: a project in Google AI Studio comes with a little free-tier trial usage — enough to learn on. The one thing to watch is the rate limit: once a project hits it, you either spin up a fresh project or wait for the next day's reset.

Tokens aren't characters

Because tokenizers work on UTF-8 bytes, token cost isn't even across languages. An English letter is one byte, but a Chinese or Japanese character is three — so a less-common character like 謝 can land as three separate tokens. The sting: the same prompt can cost several times more tokens — more money, more context — in some languages than in English. Budget by tokens, not characters.

The core mechanic, in code

No chat helper here — the demo holds the history in a plain history list and sends all of it on every call, re-sending the earlier turns each time. That's the multi-turn mechanic in the open. Reading it top to bottom:

demos/01-chatbot-python/chatbot.py 
history = []   # the model is stateless — THIS list is the only memory

while True:
    user_input = input("You: ").strip()
    history.append(types.Content(role="user", parts=[types.Part(text=user_input)]))

    # send the ENTIRE history every call — earlier turns get re-sent, the multi-turn part
    response = client.models.generate_content(
        model="gemini-2.5-flash",
        contents=history,
        config=types.GenerateContentConfig(system_instruction=SYSTEM_PROMPT),
    )

    history.append(types.Content(role="model", parts=[types.Part(text=response.text)]))
    print(f"Gemini: {response.text}")
    # response.usage_metadata.prompt_token_count = size of the context sent this turn
  1. The history list is the entire memory. The model keeps nothing between calls — if it's not in this list, it never happened.
  2. Each turn appends your message to the list as a user message before doing anything else.
  3. contents=history is the key line: the whole list is sent every call. Turn 3 only knows about turn 1 because turn 1 is still in this list, re-sent along with everything else.
  4. The reply is appended back as a model message so the next turn includes it too — and usage_metadata.prompt_token_count reports how big the context sent this turn was. That's what the demo prints climbing every turn: one new message, the rest previously sent.
