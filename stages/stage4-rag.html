Stage 4

RAG & embeddings

The context window is finite, so you can't paste every document into every prompt. RAG is the answer to "how do I let a model use a pile of my own data without drowning it?"

What I built

A "chat with your docs" tool in Python. It reads a folder of Android notes and answers questions using only the relevant passages — and prints which file each answer came from. Embeddings run locally through Ollama, the vectors live in a local ChromaDB, and Gemini writes the final answer from just the few passages that were retrieved.

View the demo & README on GitHub

Key concepts

  • Embedding — text turned into a list of numbers (a vector) by an embedding model, such that similar meanings land at similar numbers.
  • Chunking — splitting each document into smaller, overlapping pieces before embedding, so a match points at a paragraph, not a whole file.
  • RAG — the whole pattern: retrieve the most relevant chunks, inject only those into the prompt, then generate.

Embeddings come from an AI model

An embedding isn't a formula — it's produced by a dedicated embedding model, a neural network trained for one job: turn text into a vector so that similar meanings land near each other. It's a real AI model, just a different one from the chat LLM that writes the final answer. (Here the embedding model is nomic-embed-text, run locally via Ollama; the answer comes from Gemini.)

The one rule that matters most

Use the same embedding model for your documents and for the query. Each model lays out its vector space differently, so a question embedded by model A and a chunk embedded by model B simply aren't comparable — "nearest" only means something when both sides came from the same model. Swap the embedding model later, and you have to re-index everything.

How RAG does the search

With every chunk turned into a vector, the search itself is simple. RAG embeds your question into a vector with that same model, then asks the store for the chunk-vectors closest to it — measured by distance (this demo uses cosine distance). The nearest few are the chunks it retrieves. There's no keyword matching anywhere: two passages match because their meanings are close, so "how do I cancel async work?" can pull a passage about viewModelScope it shares not a single word with.

The pipeline

Two halves run at different times, and the vector store is the bridge between them — built once, queried over and over.

Index once (build time): read the documents, chunk each into overlapping pieces, embed every chunk, and store the vectors — alongside the original text and its source filename — in the vector store. You only redo this when the documents change.

Per question (query time): embed the question with the same model, ask the store for the top-K nearest chunk vectors, paste those chunk texts into the prompt, and let the LLM answer grounded only in them. The model never sees your whole corpus — just the handful of passages that matched.

How long is a vector? Dimensions by model

The length of an embedding is fixed by the model — every input it sees becomes a vector of exactly that size. A few, for scale:

The questions I had about the vectors

QuestionAnswer
Who decides how many dimensions a vector has? The embedding model, not you — it's a fixed property of the model (the table above). You pick the model; the model fixes the dimension count for every input.
Does one piece of text make one vector or many? One piece of text → one vector. A query is a single vector. A document becomes many vectors only because you chunk it first — one vector per chunk.
What happens as the database keeps growing? More chunks = more points to compare against. Comparing the query to every point one by one gets slow, so vector stores use an approximate-nearest-neighbour index (the demo's hnsw:space: cosine setting) to stay fast. Storage grows with the data; at real scale you reach for a dedicated vector database.

Gotchas & lessons

RAG needs scale to mean anything

RAG is built for searching at scale — its whole job is picking the best few chunks out of many. Two ways that quietly collapses on a tiny dataset:

  • Too few chunks to choose from. Retrieval returns the top-K nearest (here, 3). If you only have 3 chunks total, it returns all of them — there's nothing to filter, so the "search" is meaningless. My first runs did exactly this and listed every file for every question.
  • Documents too short to chunk. Chunking only helps when a document is long enough to split into several pieces. If each source is a few lines, it stays a single chunk and the whole benefit disappears.

So RAG earns its keep on a large corpus of reasonably-long documents; on a handful of short notes it's machinery doing nothing.

Where RAG actually fits today

Use caseStill RAG?Why
Document / knowledge-base Q&A Yes The original sweet spot — large unstructured text where meaning-based search beats keyword search.
AI web search Yes, reframed Same retrieve-then-generate shape, but the search engine's ranking is the retrieval (see below).
Coding-agent code search & memory Mostly no A real reversal: early tools embedded code, then moved away (see below).

How RAG hides inside AI web search

"Search the web" is mostly the Stage 3 tool loop wrapped around a search engine: the model writes keywords, the engine ranks pages, snippets come back, the model answers. That ranking is "retrieval" in the broad retrieve-then-generate sense — but it's the engine's own ranking, not embeddings.

So where does the embedding RAG from this stage actually appear? Only sometimes, and deeper in: when the agent opens one large page and needs the relevant part of it, it may chunk and embed that single page and pull the closest passages — classic RAG on one document. But it's optional: with big context windows the model often just reads the page or the snippets directly. The keyword search is always there; the embedding step is a maybe.

Coding agents and their own memory

One more place I expected embeddings and didn't find them: a coding agent's own memory. It generally isn't vector-based — it's a static rules file loaded in full, plus self-written notes, with a model judging which note is relevant for a turn by reading filenames and short descriptions, not by cosine similarity. Same direction as the code-search row in the table above: early tools embedded code and searched it, then moved to plain grep/read as context windows grew and because exact function and class names suit literal lookup over fuzzy matching. When exact lookup plus a model's own judgement work, vector search isn't worth its weight.

The high-level mechanism is solid, but the deep internals of one such memory system come from community analysis of a leaked build, not official docs — so trust the shape, not the specifics.

The core mechanic, in code

Retrieval is just "embed the question, ask the store for the nearest vectors." Everything clever about meaning is hidden inside that one comparison.

demos/04-rag-python/rag.py 
def retrieve(query, collection, top_k=3):
    query_vector = embed(query)                # same model that embedded the docs

    results = collection.query(
        query_embeddings=[query_vector],
        n_results=top_k,                       # only the K nearest chunks
        include=["documents", "metadatas", "distances"],
    )
    return [{"text": d, "source": m["source"], "distance": dist}
            for d, m, dist in zip(results["documents"][0],
                                   results["metadatas"][0],
                                   results["distances"][0])]
  1. embed(query) turns the question into a vector using the same embedding model that indexed the docs — they have to share a coordinate space, or "nearest" is meaningless.
  2. collection.query(...) hands that vector to the store and asks for the top_k closest chunks. The store does the nearest-neighbour search; this is the entire "retrieval."
  3. distances come back too — a smaller distance means closer in meaning. The lines I build from this are exactly what gets pasted into the prompt for the model to answer from.
