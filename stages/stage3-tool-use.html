Stage 3

Tool use / function calling

Until now the model could only talk. This is the stage where it can act — by asking my code to do things on its behalf. It's also the single most important mental model in the whole journey.

What I built

A dev assistant in Python with three tools: read a file, list a directory, and search for a keyword across files. You ask "what's in dev_assistant.py?" and it reads the real file and answers from the actual contents — not a guess. Small program, but it's the first one that reaches out and touches my machine.

Key concepts

The model never runs anything

This is the part that surprised me most. Tool use (a.k.a. function calling) does not mean the model executes code. I give it a list of described functions — name, description, parameter schema — and all the model can do is reply with a request: "call read_file with path='./x.py'." My code reads that request, runs the real function, and hands the result back. The model is the decider; my code is the hands.

How the model knows which tools exist

If it can't run anything, how does the model even know read_file is an option? You tell it. Alongside the conversation, every request carries a list of tool definitions (Gemini calls them function declarations), and each one is pure description — no code:

  • a name the model uses to request the tool,
  • a plain-English description of what it does and when to use it,
  • a parameter schema — the arguments it takes, their types, and which are required.

Because that description is all the model has to go on, its wording carries real weight: vague text gets the tool picked at the wrong moment or called with the wrong arguments. (This is the exact same shape MCP uses in Stage 5 — a tool is just a name, a description, and a schema, wherever it comes from.)

The tool call comes back structured

Here's the piece that actually makes the loop work. When the model wants a tool, it doesn't write "please read main.py" as a sentence — it returns a structured function call: a dedicated part of the response carrying the tool's name and its args as real data, not prose. Producing that exact format is a trained ability (more on that in Stage 6), and it's what lets your code react programmatically instead of trying to parse English.

So every reply is one of two shapes, and the agent tells them apart by shape — not by reading the wording:

  • has a function_call part → the model wants a tool; run it.
  • plain text, no function call → the model is done; that text is the answer.

When your code finishes the tool, it sends the outcome back the same structured way — a function_response tagged with the tool's name — so the model can read the result on its next turn. That request-and-response pair is the entire conversation between the model and a tool.

The tools most agents share

Once you've seen this pattern, you start spotting it everywhere. Most coding and agentic assistants expose a strikingly similar core toolset — the capabilities barely differ, even when the names (and the naming convention) do. The real tool names from a few:

CapabilityReal tool names (and whose)
Read a fileRead (Claude Code), read_file (Cursor, Cline)
Edit / write a fileEdit / Write (Claude Code), edit_file (Cursor), write_to_file / replace_in_file (Cline), apply_patch (Codex)
List or find filesGlob (Claude Code), list_dir (Cursor), list_files (Cline)
Search the codeGrep (Claude Code), codebase_search / grep_search (Cursor), search_files (Cline)
Run a shell commandBash (Claude Code), run_terminal_cmd (Cursor), execute_command (Cline), shell (Codex)
Search / fetch the webWebSearch / WebFetch (Claude Code), web_search (Cursor)
Ask the user a questionAskUserQuestion (Claude Code), ask_followup_question (Cline)

Even the convention differs — Claude Code uses TitleCase (Read, Bash), most others snake_case (read_file, execute_command). That last row is easy to overlook, but it's how a good agent avoids guessing: when the goal is ambiguous, it calls a tool to ask rather than barrel ahead. (You may have noticed it in action a few times already.)

My demo's three tools (read, list, search) are the small end of this same set. Each is just a name, a description, and a parameter schema — so swapping one agent's toolset for another's is mostly renaming, not reinventing.

Gotchas & lessons

The model can fake it

My first "successful" run was a lie. The model replied "Sure, I'll read that file and check…" — a fluent sentence describing a tool call it never actually made. Nothing ran. The tell is concrete: a real call prints 🔧 Executing tool: read_file(...) before the answer. No that line, no action — the model is just role-playing being an agent.

Where context bloat starts

Remember that a single request from you can spin the loop many times — the model might read one file, then another, then search, all to answer one question. Each of those rounds appends its tool result to the history and resends it, so the context window can grow a lot within one question — which raises two things worth understanding before Stage 6 has to manage them: what happens when it fills, and what happens when a single tool floods it.

What happens when the window fills up

The window is a hard cap — but hitting it usually isn't the disaster it sounds like, because good tools see it coming. Three things can happen, worst to best:

  • Hard error. The rawest case: the API simply rejects a request that's over the limit with a too-many-tokens error.
  • Blunt truncation. A naive app drops the oldest messages to make room. It won't crash, but it silently forgets the start of the conversation and can quietly get worse.
  • Context compaction. What most mature agents and chat tools actually do: as the window fills, they summarize the earlier turns into a compact form — keeping the decisions, facts, and current state, dropping the verbatim detail — and carry on.

So the honest picture is the third one. Running out of room rarely stops a good agent dead; it compresses, loses a little fidelity, and keeps going — the session continues smoothly even though some fine-grained history is gone. That summarized memory is itself part of the harness in Stage 6, which is why "the agent forgot something" is more often lossy compaction than a true crash.

The noisy-tool trap

Now imagine a tool that runs a build and returns all of its output. One call can dump thousands of lines of compiler logs straight into the context — and that single result might eat a huge slice of the window in one shot. It blows the token budget, spikes the cost, and pushes genuinely useful earlier context out the back. The fix is to never feed raw firehose output back: truncate it, or extract only the lines that matter (the error, the summary). That's exactly what Stage 6's agent does with a truncation cap on every tool result.

The core mechanic, in code

Two parts make tool use work: first you describe the tools to the model, then you run the loop that handles whatever it asks for.

Part 1 — describe the tools to the model

Each tool is declared as a name, a description, and a parameter schema — then the whole list is handed to the model so it knows what it can request.

demos/03-tool-use-python/dev_assistant.py 
# a description only — note there is no actual code in here
TOOLS = [
    {
        "name": "read_file",
        "description": "Read the contents of a file at a given path.",
        "parameters": {
            "type": "object",
            "properties": {"path": {"type": "string"}},
            "required": ["path"],
        },
    },
    # ... list_files and search_in_files are described the same way ...
]

# wrap the declarations — this is the "menu" handed to the model each request
tools_config = types.Tool(function_declarations=[types.FunctionDeclaration(**t) for t in TOOLS])
  1. Each entry is a description, not code — a name, a description, and a parameters schema (the JSON-style types, and which arguments are required).
  2. These words are the model's only knowledge of the tool. It never sees the body of read_file, so vague descriptions here are exactly what make it pick the wrong tool or pass bad arguments.
  3. tools_config wraps the declarations; it's then passed on every request, so the model always sees the menu. The real read_file function — and the execute_tool router that maps a name back to it — live elsewhere in the file. Declaration and implementation are deliberately separate.

Part 2 — run the loop

With the menu attached, the loop collects any tool requests, executes each, appends the results, and repeats:

demos/03-tool-use-python/dev_assistant.py 
while True:
    response = client.models.generate_content(
        model="gemini-2.5-flash", contents=contents,
        config=types.GenerateContentConfig(system_instruction=SYSTEM_PROMPT, tools=[tools_config]),
    )
    parts = response.candidates[0].content.parts

    calls = [p.function_call for p in parts if p.function_call]

    if not calls:                              # no request → this IS the answer
        return "".join(p.text for p in parts if p.text)

    contents.append(response.candidates[0].content)   # the model's turn
    for call in calls:
        result = execute_tool(call.name, dict(call.args))   # MY code runs it
        contents.append(types.Content(role="user", parts=[types.Part(
            function_response=types.FunctionResponse(name=call.name, response={"result": result}))]))
  1. The loop sends the whole contents list to the model each time around — same growing history as Stage 1, plus the tool menu from Part 1.
  2. It checks each part for a function_call. That structured part — not any English in the text — is how the loop detects the model wants a tool; a reply can hold plain text, a function call, or both.
  3. No function call means we're done — that reply is the final answer and the loop returns it.
  4. Otherwise, for each call, execute_tool runs the real function (the line where my code, not the model, acts), and the outcome goes back as a structured function_response tagged with the tool's name. Then the loop repeats with the result in hand — which is also where the context starts growing.
